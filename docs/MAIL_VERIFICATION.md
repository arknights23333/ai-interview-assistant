# 邮箱验证码用途约定

## 发送请求

`POST /api/user/auth/sendMail` 允许未登录访问，请求体必须包含邮箱和验证码用途：

```json
{
  "email": "user@example.com",
  "scene": "REGISTER"
}
```

`scene` 为以下大写枚举值之一：

| scene | 用途 | 验证码键前缀 |
| --- | --- | --- |
| REGISTER | 注册 | auth:mail:code:register: |
| RESET_PASSWORD | 忘记密码后重置密码 | auth:mail:code:reset-password: |
| CHANGE_PASSWORD | 已登录后通过邮箱验证码修改密码 | auth:mail:code:change-password: |
| CHANGE_EMAIL | 已登录后改绑邮箱 | auth:mail:code:change-email: |

实际验证码键由前缀与规范化后的邮箱拼接。邮箱规范化仅将最后一个 `@` 后的域名转为小写，保留本地部分的大小写；发送、消费、绑定比较和注册存储使用同一规则。限流键也使用规范化邮箱。前端只能选择用途，不能提交 Redis 键或前缀。注册、修改密码等业务消费验证码时使用服务端固定前缀，不从请求中决定消费用途。

不传 `scene` 或传 `null` 时，返回 HTTP 400、业务码 40000，提示“请选择验证码用途”。非法枚举值或请求体解析失败也返回 HTTP 400、业务码 40000。

## 存储与消费

- 六位字母数字混合验证码有效期为 120 秒。
- 同一邮箱的所有用途共享 60 秒发送间隔，限流键沿用 `auth:mail:limit` + 邮箱。例如，刚发送注册验证码后，立即申请重置密码验证码也会被限流。
- Lua 原子检查限流并写入对应用途的验证码键和共享限流键。
- SMTP 发送失败时，仅比较并删除本次写入的验证码，保留共享限流键。
- 校验继续使用同一份 Lua：键不存在返回 0；不匹配返回 -1 且保留验证码；匹配后删除并返回 1。
- 不同用途互不覆盖、不能相互消费。跨用途校验在目标用途没有验证码时提示过期；目标用途已有其他验证码时提示不匹配。
- `verifyAndConsumeMailCode(keyPrefix, email, code)` 的前缀由内部业务调用方固定传入。

已有注册流程固定消费 REGISTER，已登录修改密码固定消费 CHANGE_PASSWORD。RESET_PASSWORD 的发送用途及前缀已预留，重置密码接口尚待实现；后续必须固定消费该前缀。

此次不读取旧的通用 `auth:mail:code:` + 邮箱键，不提供跨用途兼容回退。部署后旧验证码需重新申请，旧键会按原有效期自行过期。

## Apifox 手动验证

1. 向发送接口提交 REGISTER，确认仅生成注册用途键，返回体不包含验证码。
2. 同一邮箱 60 秒内切换任一用途再次发送，确认仍然被限流。
3. 等共享限流过期后发送 CHANGE_PASSWORD，确认注册用途验证码未被覆盖（两分钟有效期内）。
4. 用注册邮件的验证码调用修改密码，确认校验失败，且不会删除注册用途验证码。
5. 用修改密码邮件的验证码修改当前账号密码，确认验证成功、对应验证码被删除、登录会话失效。
6. 发送 RESET_PASSWORD，确认写入重置密码用途键；实际重置流程待对应接口完成后验证。
7. 不传 scene、传 null 或传未知用途，确认返回 HTTP 400 和业务码 40000，不发送邮件、不写验证码键。
8. 按用途检查错误、过期、重复消费和发送失败后的清理；发送失败不得清理其他用途的验证码。
